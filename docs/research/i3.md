# i3 — research note for Rovr

Scope: what i3 is, the design ideas that have aged well across a
decade of tiling-WM history, the ideas that have aged poorly, and
what that means for Rovr. i3 is the spiritual ancestor of Aerospace
and a major influence on every modern tiling WM. Reading i3 is
cheaper than reading the rest of the ecosystem; it concentrates the
ideas.

Source materials: the i3 userguide, the IPC spec, the `tree.c` and
`ipc.c` source files, and the Sway-from-scratch reimplementation as
a cross-check.

## 1. What i3 actually is

- A tiling WM for X11, written in C. Original author Michael
  Stapelberg, first release 2009. Active project, ~12k GitHub stars
  on the i3 repo and ~14k on i3-gaps (the popular gap-patched fork).
- A dynamic tree-based WM: windows are placed automatically into a
  tree that the user reshapes with commands.
- Pure X11, no compositing. No animations. Built for keyboard
  primary, mouse optional, dotfile-only configuration.
- Three external siblings: i3bar (status bar), i3status (status
  generator), i3lock (screen locker). All separate binaries. i3
  itself is just the WM.

## 2. The data structure: one Con type for everything

This is i3's single most copied idea. From the source:

> The `Con` structure is the cornerstone of i3's architecture. It
> represents everything from the root container to individual windows
> in a unified structure, which simplifies operations on the
> container tree.

The same struct holds the X11 root, outputs, dock areas, content
areas, workspaces, split containers, and window containers. A `type`
field discriminates. The tree is a doubly-linked structure using
`TAILQ` macros; the tree is rendered top-down and events are
processed bottom-up.

Why this matters:

- Every tree operation has one shape: "find a `Con`, mutate, re-render."
- "Workspace" and "split container" and "window" are all just
  positions in the same tree. There's no special case for any of
  them in the rendering or focus code.
- The whole tree can be walked in O(n) by following `nodes_head` /
  `floating_head` linked lists from the root.

What it costs:

- The `type` field is a runtime tag, so invalid states (e.g. a
  floating window with no parent) are possible and the code has
  to defend against them. A tagged union in Rust gives us the same
  expressivity with a guarantee that the tag matches the data.
- The tree is mutable. Race conditions during event handling are
  possible and i3 has to be careful about re-entrancy. Aerospace
  has been paying for this for years; their `#1215` refactor to
  an immutable persistent tree is the same lesson.

Rovr takeaway: take the "one type, one tree" idea, but encode it
with a Rust enum + immutable state, not a tagged struct +
mutability. The point of i3's design was the *uniformity*; the
*mechanism* was a C-era compromise.

## 3. The command surface: a string grammar, parser-generated

i3 parses commands with a Yacc/Bison grammar in `parser/src/cmdparser.y`.
The grammar is a real LALR(1) parser, ~thousand lines. The output is
a parse tree that the dispatcher walks.

The command surface is large. The userguide documents ~50
commands, including:

- `exec`, `exec_always` (with `--no-startup-id`)
- `split vertical|horizontal|toggle`
- `layout default|tabbed|stacking|splitv|splith`
- `layout toggle [split|tabbed|stacking|splitv|splith] [...]`
  (cycle through up to four)
- `fullscreen enable|disable|toggle|toggle global`
- `floating enable|disable|toggle`
- `focus <criteria> | workspace | left|right|down|up | parent | child
  | next|prev | floating | tiling | mode_toggle | output <dir|name>`
- `move <left|right|down|up> [<amount> [px|ppt]]`
- `move position <x> [px|ppt] <y> [px|ppt]`
- `move [absolute] position center`
- `move container|window to workspace <name>` (with `back_and_forth`,
  `prev|next|current`, `next_on_output|prev_on_output`)
- `move container|window to mark <mark>`
- `move container|workspace to output <dir|name>`
- `swap container with id|con_id|mark <arg>`
- `sticky enable|disable|toggle`
- `rename workspace <old> to <new>`
- `mark [--add|--replace] [--toggle] <identifier>`
- `workspace next|prev|next_on_output|prev_on_output | back_and_forth |
  [--no-auto-back-and-forth] <name>`
- `bar hidden_state <hide|show|toggle> [<bar_id>]`
- `bar mode <dock|hide|invisible|toggle> [<bar_id>]`
- `gaps inner|outer|horizontal|vertical|... current|all
  set|plus|minus|toggle <n>`
- `border normal|pixel|toggle|none [<n>]`
- `title_format <format>`, `title_window_icon <yes|no>`
- `shmlog <size>|on|off|toggle`, `debuglog on|off|toggle`
- `reload`, `restart`, `exit`
- `move scratchpad`, `scratchpad show`
- `kill`, `nop <comment>`, `mode <name>`

Plus a separate, *prefixed* command-criteria language: any command
can be preceded by `[class="..."] [instance="..."] [title="..."]
[con_mark="..."] [con_id="N"] [workspace="..."] [urgent] [tiling]
[floating] [...]` to scope the command to matching windows.

This is enormously influential. Every modern tiling WM has copied
the command surface, in some form. Aerospace copied most of it
verbatim. Sway preserved it as a hard compat target. Hyprland and
Niri each have their own flavor.

Rovr takeaway: the *concept* (one large command surface, with a
criteria language for selecting targets) is right. The *mechanism*
(yacc grammar + string parsing at runtime) is a 2009 decision that
Rust can do strictly better:

- A typed `Command` enum in Rust gives us the same expressivity
  with no parse step at runtime. The command surface is
  declarative, exhaustively matched, and trivially serializable
  to JSON for IPC and to clap for CLI.
- The criteria language is its own DSL and deserves the same
  treatment: a small typed `Selector` enum with regex / equality
  semantics, and an evaluator that walks the window tree.
- The "criteria prefix before any command" pattern is a real
  ergonomic win. We should keep it. In Rust it can be
  `Selector::default().class("Firefox")` as a builder, or a
  compact string form for the IPC payload, with the same surface
  in both.

What to *not* take from i3's command surface:

- `mode <name>` as a *separate command* (vs. Aerospace's `[mode.X.binding]`
  block). i3's `mode "launcher" { bindsym f exec firefox }` puts
  the bindings in the config and a runtime `mode launcher` enters
  them. This is exactly the i3/Aerospace shared pattern; we're
  already taking it.
- `shmlog` (shared-memory log buffer) is a debugging hack that
  probably doesn't earn its place in a Rust daemon with proper
  structured logging.
- `restart` (the in-place restart that inherits the IPC socket
  fd) is clever but it's also a Yabai-style "the daemon is fragile
  enough that we need to be able to swap the binary under it." A
  clean shutdown + supervised restart is simpler.

## 4. The IPC contract: minimal, versioned by message type, JSON over Unix socket

i3's IPC is the original. Spec is at `i3wm.org/docs/ipc.html`.
Key facts:

- Unix domain socket at `$XDG_RUNTIME_DIR/i3/ipc-socket.%p` or
  `/tmp/i3-%u.XXXXXX/ipc-socket.%p`. `%p` is the PID, `%u` is the
  user, `XXXXXX` is a `mkdtemp` random.
- Wire format: 6-byte magic string (`"i3-ipc"`) + 4-byte native
  payload length + 4-byte native message type + JSON payload.
  Native byte order, *no explicit version field*. The magic string
  is the version: "if you don't say i3-ipc, you're talking to the
  wrong daemon."
- 13 message types (RUN_COMMAND, GET_WORKSPACES, SUBSCRIBE,
  GET_OUTPUTS, GET_TREE, GET_MARKS, GET_BAR_CONFIG, GET_VERSION,
  GET_BINDING_MODES, GET_CONFIG, SEND_TICK, SYNC,
  GET_BINDING_STATE).
- Reply is the same header format with a different message-type
  value. Events share the same frame format but with the high bit
  of the type set.
- Reply/event payloads are always JSON. yajl generates them
  server-side.
- SUBSCRIBE: payload is a JSON array of event-type strings. The
  server replies once and then sends event frames on the same
  connection until the client closes.
- No timeout on subscribe, no heartbeat, no backpressure. Clients
  that read slowly block the daemon's IPC write.

Rovr takeaway: the *contract* is the right one. The *specifics*
should be tightened:

- Skip the magic-string "version." Use an explicit
  `SOCKET_PROTOCOL_VERSION` u32, like Aerospace.
- Magic string or not, the framing (length-prefix + JSON) is good.
  Keep it.
- Subscribe-mode on the same socket is fine for now, but plan to
  split into control + event sockets. See the Aerospace #1514
  growth pain.
- The "high bit of the message type means event" trick is a
  clever bit-saver, but the right answer is a 4-byte length, a
  1-byte kind (control vs event vs notify), and a 1-byte
  reserved/padding byte. The 8 bytes become 6. The complexity
  moves into the type system, not the wire format.
- The lack of a heartbeat on subscribe is a real bug. A bar that
  has been blocked on a syscall for 5 minutes will not notice the
  daemon is gone. We need either a keepalive message or a
  TCP-style `KEEPALIVE` socket option.
- The 2048-byte max-message-size is an old limit. We should use
  a sane default (64 KiB like Nehir/OmniWM) and document a way
  to grow it for large GET_TREE replies.
- The 13 message types are a good surface for the read side. We
  should add: `GET_RULES`, `GET_BINDINGS` (the active resolved
  binding table, not just modes), and `GET_CAPABILITIES` (which
  platform features are usable, as a single source of truth for
  the `macos == Sonoma` problem from `PRODUCT.md`).

Concrete suggestion for the wire format:

```
+--------+--------+--------------------+
| 4B len | 1B kind| JSON payload (UTF-8) |
+--------+--------+--------------------+

kind: 0 = control request, 1 = control reply,
      2 = event (server-pushed), 3 = error
```

The `len` does *not* count itself or the kind byte. JSON is the
payload format. The reply to a request always echoes the request's
id, so a client with concurrent requests can match them.

## 5. The config: a domain-specific text format, not TOML

i3's config is its own format. It is not TOML, not YAML, not
s-expressions. It is a hand-rolled, line-oriented, line-typed
format with C-style `#` comments and a small set of directives.

The directives include:

- `bindsym` / `bindcode` — key bindings
- `mode` — define a binding mode
- `for_window` — window rules
- `assign` — automatic workspace assignment
- `exec` / `exec_always` — startup commands
- `floating_modifier`, `default_orientation`, `workspace_layout`,
  `default_border`, `hide_edge_borders`, `focus_follows_mouse`,
  `mouse_warping`, `popup_during_fullscreen`, `focus_wrapping`,
  `workspace_auto_back_and_forth`, `force_display_urgency_hint`,
  `focus_on_window_activation`
- `client.<colorclass> <border> <bg> <text> <indicator>
  <child_border>` — theme
- `bar { ... }` — bar block (defines a status bar config)
- `include <pattern>` — file include
- `set $<name> <value>` — variable
- `font pango:...` — title font

There is no schema. Adding a new directive means editing
`parser/src/config_parser.y` and the config code in `config.c`.

Rovr already has the answer in `PRODUCT.md`: TOML. We should not
revisit this. But we should learn from i3's config:

- **Typed keys, not strings.** `bindsym $mod+Shift+r restart` is
  ergonomic but `bindsym` cannot be statically checked. In TOML
  we can do `bindsym = [{ key = "Shift+Mod1+r", mode = "default",
  command = "restart" }]` and have the schema enforce that
  `command` is a known command.
- **The `bar { }` block in i3 has been a source of pain.** It's
  half-config, half-program. i3status is a separate process and
  its output is a separate config. We should not embed the bar
  config; keep that as a user-side choice and just provide
  *events* the bar can subscribe to.
- **`include` is a useful feature.** i3's include is shell-like
  and supports `~`, env vars, wildcards, command substitution. We
  can do the same with `serde` + a small expansion pass. Keep
  it, but make sure included files are *additive* — i3 documents
  that they cannot undo earlier config, which is the right call.
- **`set` for variables is a workaround for the lack of types.**
  Real variables are a power tool; for a first cut, the TOML
  config should just inline the values and we can add a macro
  layer later if needed.

## 6. The criteria language: a tiny DSL that travels everywhere

i3's criteria are the most-reused design idea in the whole
project. They appear:

- As a prefix on any command: `[class="Firefox"] focus`
- In `for_window <criteria> <command>` config rules
- In `assign <criteria> <workspace>` automatic assignments
- In `i3-msg` queries

The grammar is:

```
[ class="regex"     ]
[ instance="regex"  ]
[ title="regex"     ]
[ con_mark="regex"  ]
[ con_id="N"        ]
[ window_role="…"   ]
[ workspace="name"  ]
[ machine="name"    ]
[ urgent            ]
[ tiling | floating ]
[ all               ]
```

Each criterion is a PCRE regex (or, for `con_id`, an exact number,
or, for `urgent`/`tiling`/`floating`/`all`, a boolean flag). When
multiple criteria appear in one bracket group, they are AND-ed. To
OR, use multiple bracket groups: `[class="A"] [class="B"] focus`.

This is *the* reason i3 configs are short. You can write
`for_window [class="Firefox"] fullscreen enable` and it just
works. The same power, expressed in Aerospace's `on-window-detected`
TOML, takes three lines:

```toml
[[on-window-detected]]
if.app-id = 'org.mozilla.firefox'
run = 'fullscreen enable'
```

Both work. i3's is shorter. The TOML version is more checkable.

Rovr takeaway: keep i3's criteria shape, but in Rust. The right
representation is a `Selector` enum:

```rust
pub enum Selector {
    All,
    AppId(AppIdPattern),      // regex
    WindowTitle(TitlePattern),
    WindowRole(RolePattern),
    ConMark(MarkPattern),
    ConId(ContainerId),
    Workspace(WorkspaceName),
    Tiling,
    Floating,
    Urgent,
    // ... combinators
}

pub struct Predicate {
    pub all_of: Vec<Selector>,   // implicit AND
}
```

A binding or rule value is `(Predicate, Vec<Command>)`. This gives
us i3's prefix syntax (`[class="A"] focus`) as a `Predicate` with
one `Selector`, and i3's multi-bracket OR as `Vec<Predicate>`.

The string syntax can still exist for config files and CLI — but
it deserializes into the typed enum, and *only* the typed enum is
the source of truth. The parser is the adapter, not the model.

## 7. The render loop: tree mutation then full re-render

i3's render path is, briefly:

1. Event handler mutates the `Con` tree in place.
2. `tree_render()` walks the entire tree top-down.
3. Each container is "rendered" — its position/size is computed
   from its parent and its children, and the `x_push_changes()`
   call at the end pushes everything to X11 in one go.

This is "mutate then dump" rather than "subscribe to state changes
and diff the changes." It's simple and predictable. The cost is
that every event triggers a full tree walk, even for trivial
changes. With ~10-100 windows this is fine; with 1000+ it shows.

Rovr takeaway: take "mutate then re-render" as the rendering
discipline. Specifically:

- The reconciler is the only place that mutates `DesiredState`.
  Bindings and rules are pure functions: `DesiredState -> Command
  -> DesiredState`.
- The reconciler computes the diff and emits a batch of platform
  actions. The platform layer executes them.
- The reconciler is *idempotent* (Aerospace's `refreshSession`).
  Calling it twice with no input change must be a no-op on the
  platform.
- Property test: `reconcile(reconcile(state)) == reconcile(state)`.

What i3 does *not* do that we should:

- i3 has no concept of "verify after mutation." It calls X11 and
  assumes it worked. Aerospace has the same gap and is paying for
  it. We should `enumerateWindows()` after sensitive platform
  actions and reconcile again. `PRODUCT.md` calls this out
  explicitly: "After sensitive operations, Rovr re-observes the
  affected state and verifies the result."

## 8. What i3 doesn't have that Rovr will

These are the things `PRODUCT.md` says we should build and that
i3 deliberately doesn't try to:

- **Hot-reload of config.** i3 has `reload` but it requires
  restarting to apply some changes (notably key bindings in
  `mode` blocks). We should ship transactional hot-reload.
- **State persistence.** i3 does not remember your windows across
  restart. You re-open everything manually. Rovr's
  `persistent_workspaces` + restoration is a clear win.
- **Sticky windows.** i3 has `sticky enable` but it only works
  on floating windows and only for one window at a time. We
  should treat sticky as a first-class layout mode.
- **Scratchpads.** i3 has scratchpads but they're one-binary; you
  can't have multiple named scratchpads. Aerospace has the same
  limit. Multiple named scratchpads is high-value.
- **Reactive rules that aren't just window-creation.** i3 has
  `for_window` and `assign`, both of which fire when a window
  appears. There's no `on_focus_change`, `on_workspace_change`,
  `on_display_change`. Aerospace has these. We should too.
- **Typed errors with stable codes.** i3 returns a single
  `{"success": true|false}` from `RUN_COMMAND` and the rest of
  the error message is in stderr. Aerospace does better with
  exit codes. We should do better than both: structured error
  envelopes with codes, a documented catalogue, and a typed
  error type on the Rust side.
- **A flight recorder.** i3 has `shmlog` and `debuglog`, both of
  which are circular buffers you dump on request. They work but
  they are not queryable and they don't survive a crash.
  `PRODUCT.md` calls for a structured, bounded, queryable
  flight recorder. The right model: a `tracing`/`tracing-subscriber`
  sink into a ring buffer of recent events, exposed over IPC as
  `GET_FLIGHT_RECORDER [--since <id>] [--filter <pattern>]`.
- **Per-app async platform queries with timeouts.** i3 doesn't
  have this problem because X11 is cooperative in a way
  Accessibility isn't. The macOS equivalent is `AXUIElement` and
  we already know from the Aerospace research that it blocks. We
  need a platform worker pool from day one.

## 9. Sway as a forward reference: what "i3 in Rust" looks like

Sway is a from-scratch i3-compatible WM written in Rust for
Wayland. It is the closest existing reference for "what does the
i3 user-facing surface look like in a Rust codebase." Worth noting:

- Sway uses `clap` for CLI parsing.
- Sway's IPC is line-delimited JSON, not the binary-header
  format. Cleaner for debugging, slightly less efficient. Either
  is defensible.
- Sway preserves the i3 config format for compat, but the parser
  is hand-written (no yacc). This is what we should do for the
  i3-compat shim if we ever ship one.
- Sway's command surface is *not* generated from a single source
  of truth. Each command is its own struct with its own parser.
  This is the antipattern we should avoid — see `PRODUCT.md`'s
  "Do not reproduce Yabai's giant string-command parser." A
  `Command` enum in Rovr is the right answer; derive clap,
  derive serde, and we get CLI + IPC + completion from one
  definition.
- Sway's tree uses `Rc<RefCell<Node>>` in places. Rust gives
  us better options (Arena, generational indices, or, in our
  case, the immutable persistent values that Aerospace is
  refactoring toward).

## 10. i3's non-values: what we explicitly should not copy

- **A hand-rolled config format.** TOML wins.
- **Yacc/bison command parser.** A typed `Command` enum wins.
- **Mutability everywhere.** An immutable persistent value with
  generations wins.
- **A separate "bar" config language embedded in the WM.** Keep
  the bar as a separate concern; we provide events.
- **The `restart` / hot-restart pattern as a primary
  reliability mechanism.** A clean shutdown supervised by
  `launchd` is simpler and more correct.
- **The lack of a heartbeat on subscribe.** Add one.
- **Stringly-typed config directives whose only validation is
  "if yacc accepted it."** Validate at parse time, in Rust types.

## 11. What i3 absolutely gets right

These ideas have aged perfectly. Take them whole.

- **One tree of containers for everything, including the
  workspaces themselves.** Workspaces are just containers
  with a name. The same operations work on them.
- **Per-container orientation (horizontal/vertical).** The tree
  is a real binary tree, not a 1D list.
- **Cardinal focus and move.** `focus left|right|up|down` and
  `move left|right|up|down` are the four most-used bindings in
  every i3 user survey. The mental model is so good that
  Aerospace and Sway have kept the same keyboard positions.
- **Cardinal move with `position center` and `position mouse`**
  for floating windows. Simple, obvious, complete.
- **Vim-like marks.** `mark a` / `[con_mark="a"] focus`. A
  poor-man's jump-to-anywhere.
- **Scratchpads.** A single `move scratchpad` / `scratchpad show`
  pair, plus a key to toggle, is the single most-loved i3
  feature by many users.
- **A `for_window` reactive rules engine.** Pre-dates every
  modern event-driven WM. We have this in our spec as `Rules`.
- **`focus_wrapping`** with three values (`yes`, `no`, `force`,
  `workspace`) is a small but very high-leverage piece of UX.
  The right answer at the right granularity.
- **`popup_during_fullscreen smart`** is the kind of policy
  decision most WMs punt on. i3 puts it in the config. We
  should have analogues for the macOS annoyances: popover
  windows from notifications, Mission Control popups, Stage
  Manager transitions.
- **A typed keybinding modifier `$mod`.** Letting the user
  define `set $mod Mod4` once and have the whole config inherit
  it. Small, but it makes the config portable across machines.
- **Errors that go to stderr, not a GUI dialog.** i3 has no GUI.
  Errors appear in the i3 log file and in stderr from `i3-msg`.
  The user is expected to read them. This is the right default.

## 12. Direct lifts for Rovr

1. **One tree of typed containers for everything.** The same
   struct holds workspaces, splits, windows, and floating
   windows. Discriminated by an enum.
2. **`Command` and `Selector` as the only user-facing types.**
   One enum each, derived for serde + clap + shell completion.
3. **Cardinal focus/move/swap as the primitive window
   operations.** The four-way directional model is the one
   every user knows. Don't reinvent it.
4. **A `for_window` rule engine that runs on every relevant
   event, with criteria as a typed `Selector`.** Same shape as
   i3, but typed.
5. **Vim-like marks.** `mark a` / `[con_mark="a"] focus`. Trivial
   to implement, beloved by users.
6. **Scratchpads with multiple named instances.** Lift i3's
   shape; fix the "only one scratchpad" limitation.
7. **`popup_during_fullscreen smart` analogues for macOS
   annoyances.** Document the policy decisions we make about
   popovers, Stage Manager, Mission Control, and `Displays have
   separate Spaces`.
8. **A `restart` command that performs a clean shutdown and
   relies on `launchd` supervision.** Not i3's
   inherit-the-socket-fd trick. That trick is cute, not
   correct.
9. **Workspace numbers that are also names** (`"1: www"`).
   Number is the stable identifier, name is the user-visible
   label.
10. **An `include` directive in the config.** Shell-expanded
    glob. Additive only.

## 13. Things we explicitly invert

- **Config format.** i3's hand-rolled parser becomes TOML.
- **Command parser.** i3's yacc grammar becomes a typed `Command`
  enum.
- **Tree mutability.** i3's mutable linked `Con` becomes
  immutable persistent values with generations (the same
  direction Aerospace is refactoring toward).
- **Reactive rules scope.** i3's `for_window` + `assign` is
  a window-creation-only engine. Rovr's `Rules` should run on
  every event: window created, window focused, workspace
  changed, display changed, mode changed, daemon started.
- **State persistence.** i3 has none. We have
  `persistent_workspaces` and a `flight recorder` from day one.
- **Error surface.** i3's boolean `success: false` + stderr
  becomes a typed error envelope with stable codes, queryable
  in `--json` mode.
- **The bar.** i3's `bar { }` block is half the config and
  half a debug nightmare. We emit events; bars consume them.

## 14. What the i3 / Sway / Aerospace lineage teaches us

The three projects together cover the design space of "i3-style
tiling WMs":

- **i3** is the canonical command surface, the canonical
  criteria language, and the canonical config ergonomics. But
  it's C, mutable, and the IPC contract is loose.
- **Sway** shows that "i3 in Rust" is feasible and that the
  i3 surface can survive a from-scratch reimplementation
  without losing users. The cost is that the per-command
  duplication has grown large. Don't make the same mistake.
- **Aerospace** is i3 for macOS, and it's the proof that the
  macOS stack is harder than X11 in three specific ways:
  Accessibility API blocks, macOS Spaces are hostile, and
  private APIs are brittle. The `refreshSession` pattern is
  the answer to all three.

Rovr sits in the same lineage. The right move is to take i3's
ergonomics, Sway's portability story, Aerospace's
reconciliation pattern, and Rust's type system, and assemble
them into a project that is "i3 for macOS, written in Rust,
with a single typed `Command` source of truth, immutable
state, and an architecture that respects how macOS actually
behaves."

## 15. Open questions for Rovr

- Do we keep the i3-style criteria prefix in the IPC payload, or
  only in the config? (i3 has it in both. Aerospace put it only
  in config and uses `--window-id` / `--workspace` in the IPC.
  Both work. The IPC-prefix is more expressive but more
  ambiguous when criteria match multiple windows.)
- Do we ship a config-format compat shim that reads
  `~/.i3/config`? Sway does. The benefit is free migration for
  the i3-literate. The cost is a second parser to maintain
  forever. Probably not worth it.
- Do we keep `exec_always` semantics? i3 distinguishes `exec`
  (run on daemon start, not on restart) from `exec_always` (run
  every time). This is useful but only because i3 supports
  in-place restart. If we don't, `exec` covers everything.
- Do we want `popup_during_fullscreen smart` analogues for
